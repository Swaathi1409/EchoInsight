# Architecture Decisions

## ADR-001: Do Not Commit Raw Dataset Rows

**Date**: 2026-10-02
**Status**: Accepted

**Decision**: Do not commit any raw rows from the `talkmap/telecom-conversation-corpus` dataset to the repository. Commit only manifests (conversation ID lists) and fetch scripts.

**Alternatives considered**:
- Commit a 50-conversation sample. Rejected: the dataset's MIT license does not clearly address redistribution of rows generated by an unspecified LLM, which may have had restrictive generation terms. The risk is low but the cost of not committing is also low.
- Download and store locally. Acceptable for development; instructions in README.

**Why**: License clarity takes precedence. Manifests are reproducible from seed + revision.

**Trade-offs**: Setup requires a network call to the HuggingFace API. Mitigated by a fetch script that caches locally.

## ADR-002: LLM Model Selection

**Date**: 2026-10-02
**Status**: Accepted

**Decision**:
- **Primary model**: `qwen/qwen3.8-27b` (131k context window, Alibaba Cloud via Groq)
- **Verifier model**: `openai/gpt-oss-20b` (131k context window, OpenAI via Groq)
- Temperature: 0 for all production calls
- Config keys: `LLM_PRIMARY_MODEL`, `LLM_VERIFIER_MODEL`

**Evidence**:
- Only 11 models are accessible on this API key. Standard Llama/Mixtral/Gemma models returned HTTP 404.
- `qwen/qwen3.8-27b`: Verified inference (returns content), verified json_schema strict mode, measured 171 tokens per simple per-turn call.
- `openai/gpt-oss-20b`: Verified inference, verified json_schema strict mode.
- `openai/gpt-oss-120b`: Inference works but returned empty string on short prompts; selected as fallback/alternative, not primary.

**Alternatives considered**:
- `openai/gpt-oss-120b` as primary: Rejected; empty content on short prompts is a risk. The 20b model returns content reliably.
- `allam-2-7b`: Rejected; 4,096 token context is too small for conversation analysis (a 40-turn conversation easily exceeds 4k tokens).

**Trade-offs**:
- `qwen/qwen3.8-27b` is a 27B parameter model with fast inference on Groq hardware. No calibrated benchmark exists for this specific model on telecom QA tasks, so outputs must be evaluated on the gold set.
- Using two models from different families (Qwen and GPT) for primary and verifier increases independence of the verification step.

## ADR-003: Modular Monolith Architecture

**Date**: 2026-10-02
**Status**: Accepted

**Decision**: Build as a modular monolith with a microservice-style API boundary. Eight packages with no circular dependencies: `ingest`, `llm`, `analysis`, `state`, `qa`, `validator`, `analytics`, `api`.

**Alternatives considered**:
- Full microservices: Rejected; adds network latency, complex deployment, and operational overhead that is not justified for an MVP with one team.
- Single-file application: Rejected; unmaintainable at this scope.
- Celery + Redis for job queue: Deferred to future work; FastAPI background tasks + a jobs table are sufficient for Tier 1 and 2.

**Trade-offs**:
- Scaling a monolith means scaling all components together. Mitigated by the stateless API design and a separate worker entrypoint.
- Path to microservices is documented in docs/deployment.md.

## ADR-004: Database Selection

**Date**: 2026-10-02
**Status**: Accepted

**Decision**: PostgreSQL with SQLAlchemy 2 + Alembic for production and integration tests. SQLite in-memory for unit tests only.

**Alternatives considered**:
- SQLite everywhere: Rejected; missing row locking, JSON indexing, and concurrent write handling needed for production.
- MySQL: Rejected; PostgreSQL has better JSON support and is more commonly used in the ML/analytics ecosystem.
- NoSQL (MongoDB): Rejected; relational rollups and integrity constraints are core requirements.

**Trade-offs**: PostgreSQL requires a running server for integration tests. Mitigated by Docker Compose.

## ADR-005: Redaction-First Storage (STORE_ORIGINAL_TEXT=false)

**Date**: 2026-10-02
**Status**: Accepted

**Decision**: Default `STORE_ORIGINAL_TEXT=false`. Only redacted text, stable turn IDs, redaction placeholders by type, and content hashes of redacted text are persisted. Original text is never stored, not even in logs, embeddings, or LLM calls.

**Alternatives considered**:
- Store original text encrypted: Deferred; requires application-level encryption, restricted role, audit log per access, retention limit, and purge tests. Left as a documented disabled option.
- Store original text plaintext: Rejected; violates data minimization principle and the spirit of the assignment.

**Trade-offs**: Exact-quote verification must match the stored redacted text, not the original. This is correct behavior: all quotes shown in the UI use redacted text.

## ADR-006: Phrase Matching Strategy

**Date**: 2026-10-02
**Status**: Accepted

**Decision**: Implement a deterministic keyword/regex phrase matcher as the primary and default method. Embeddings-based matcher behind `EMBEDDINGS_ENABLED=false` feature flag.

**Alternatives considered**:
- Embeddings-only: Rejected; adds a heavy CPU dependency (fastembed/ONNX), has unverified benefit over regex for short telecom phrases, and consumes quota/compute.
- LLM-only for all phrase matching: Rejected; non-deterministic, quota-consuming, harder to audit.

**Trade-offs**: Keyword matching may miss paraphrases. This is explicitly measured on the labeled dev set and reported. Embeddings are enabled only if they measurably improve recall on that dev set without precision loss.

## ADR-007: Job Queue Implementation

**Date**: 2026-10-02
**Status**: Accepted

**Decision**: FastAPI background tasks with a `jobs` table (queued, running, succeeded, failed, cancelled; attempts; idempotency key) for Tier 1 and 2. Separate worker entrypoint using the same code. No Celery or Redis in MVP.

**Alternatives considered**:
- Celery + Redis: Deferred to future work. Adds deployment complexity and two new services. The jobs table provides visibility and retry logic with a single service.
- Fully synchronous: Rejected; final analysis on a 40-turn conversation can take 10-20 seconds with LLM calls. Async job with polling is necessary.

**Trade-offs**: No distributed job queue means the worker must be co-located or share the database. Horizontal scaling is limited but sufficient for MVP.

## ADR-008: Frontend Stack

**Date**: 2026-10-02
**Status**: Accepted

**Decision**: React + TypeScript + Vite + Tailwind CSS + shadcn/ui + lucide-react + Recharts + TanStack Query and Table + React Router.

**Alternatives considered**:
- Next.js: Not chosen; added server-side rendering complexity not needed for a dashboard app.
- Vanilla JS: Rejected; no type safety, harder to maintain at this component count.
- Flask templates: Rejected; does not meet the UI requirements for a rich interactive dashboard.

**Trade-offs**: Vite build must be served via a reverse proxy in production. This is handled in `docker-compose.prod.yml`.

## ADR-009: Authentication and Authorization

**Date**: 2026-10-02
**Status**: Accepted

**Decision**: Signed short-lived JWTs, argon2 password hashing, roles admin/supervisor/agent. All authorization scope derived server-side from authenticated identity and database membership, never from request parameters.

**Alternatives considered**:
- API keys: Rejected; no role-based access control or per-user auditing.
- OAuth/OIDC: Deferred; requires an identity provider. JWT is sufficient for a self-contained MVP.
- Session cookies: Rejected; harder to integrate with a stateless API and React SPA.

**Trade-offs**: Short-lived tokens require refresh logic. This is standard practice and not a meaningful burden.

## ADR-010: Synthetic Agent and Team Assignment

**Date**: 2026-10-02
**Status**: Accepted

**Decision**: Deterministic mapping from `hash(conversation_id) % 25` to 25 agents in 5 teams. Stored with `synthetic_assignment=true`. Shown with a visible "synthetic assignment" label in all UI views and API responses.

**Alternatives considered**:
- Random assignment: Rejected; not reproducible.
- Manual assignment from a real roster: Not available; no real agent data exists in the dataset.

**Trade-offs**: The synthetic assignment creates artificial performance differences between agents. These differences are meaningless for real evaluation. All agent/team analytics are labeled as synthetic in the UI and docs.
